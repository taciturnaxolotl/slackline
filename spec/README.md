# slackline specs

Everything under `src/` that starts with "This module is generated" comes from
the files in this directory. Edit the specs, then run:

```sh
cd codegen
gleam run -m slackline_codegen/generate             # regenerate src/ and test/slackline_examples_test.gleam
gleam run -m slackline_codegen/generate -- --check  # fail if any generated file is stale
gleam run -m slackline_codegen/generate -- --report # methods that still return raw json
cd ..
gleam build && gleam test                           # Erlang
gleam test --target javascript                      # JavaScript
```

The generator and the docs tools are a separate Gleam project in `codegen/`.
They never ship with the package, and they still run when the generated code
does not compile. Run them from `codegen/` or from the project root. Gleam
only passes flags such as `--check` to a program after a `--` separator.
Generated files start with
``//// This module is generated by `gleam run -m slackline_codegen/generate`. Do not edit it by hand.``

The source of truth is the official reference at <https://docs.slack.dev>.
In `codegen/`, `gleam run -m slackline_codegen/docs fetch` downloads it into `.docs/`, one
markdown file per page (`gleam run -m slackline_codegen/docs split <file> [dir]`
does the same from a local copy of `llms-full-platform.txt`). For example
`.docs/reference/methods/chat.postMessage.md` or
`.docs/reference/block-kit/blocks/section-block.md`. Read those pages, not
other SDKs, when deciding what a type looks like. Other SDKs (including
slack-edge) are known to be incomplete or wrong in places.

`methods.json` is extracted from the method pages by
`gleam run -m slackline_codegen/docs extract [docs-dir]` (default `.docs`): names,
descriptions, arguments, argument types, scopes, rate limits, errors and
response examples. The extractor writes one method per line, so a change to
one method changes one line. Do not edit the file by hand. Run the extractor
again.

## Layout

| spec file | Gleam module | contents |
| --- | --- | --- |
| `types/common.sls` | `slackline/common` | types that several modules share |
| `types/block.sls` | `slackline/block`, `slackline/element` (+ `block/*`, `element/*`) | Block Kit blocks, elements, composition objects, rich text, and their builders |
| `types/view.sls` | `slackline/view` | modals, App Home, view state |
| `types/attachment.sls` | `slackline/attachment` | legacy secondary attachments |
| `types/file.sls` | `slackline/file` | file objects |
| `types/message.sls` | `slackline/message` | message objects, metadata, reactions |
| `types/user.sls` | `slackline/user` | users and profiles |
| `types/team.sls` | `slackline/team` | workspaces and enterprises |
| `types/bot.sls` | `slackline/bot` | bot users |
| `types/usergroup.sls` | `slackline/usergroup` | user groups |
| `types/conversation.sls` | `slackline/conversation` | channels, DMs, MPIMs |
| `types/event.sls` | `slackline/event` | Events API envelopes and every event |
| `types/interaction.sls` | `slackline/interaction` | interactivity payloads and responses |
| `types/command.sls` | `slackline/command` | slash command payloads |
| `types/manifest.sls` | `slackline/manifest` | app manifests |
| `types/socket_mode.sls` | `slackline/socket_mode` | Socket Mode envelopes and acknowledgements |
| `api/<family>.sls` | `slackline/api/<family>` (+ `<family>/<method>`) | Web API methods (and the setters for their optional arguments) |

Methods default to the module `slackline/api/<first segment>` (or
`slackline/api/admin/<second segment>` for `admin.*`), and the function name is
the rest of the method name in snake case: `chat.scheduledMessages.list`
becomes `chat.scheduled_messages_list`. Methods without a spec are still
generated, with types from the docs and a raw `Value` response.

### Dependency order

Gleam modules cannot import each other in a cycle, so a module may only
reference types from modules above it in this list:

1. `slackline` (hand-written, provides `ResponseMetadata`), `slackline/value`
   (built in as `Value`), `slackline/common`
2. `slackline/block`, then the generated `slackline/element` and the
   `block/*` and `element/*` attribute modules
3. `slackline/view`, `slackline/attachment`
4. `slackline/file`
5. `slackline/message`
6. `slackline/user`, `slackline/team`, `slackline/bot`
7. `slackline/usergroup`
8. `slackline/conversation`
9. `slackline/event`, `slackline/interaction`, `slackline/command`,
   `slackline/manifest`, `slackline/socket_mode`
10. `slackline/api/*`

### Contract names

Other modules rely on these names existing. Keep them, even while you change
what is inside:

- `slackline` (hand-written in `src/slackline.gleam`): `ResponseMetadata`,
  which specs refer to by its bare name like any declared type
- `slackline/block`: `Block`, `Text`, `Element`, `SelectOption`, `OptionGroup`, `ConfirmationDialog`
- `slackline/view`: `View`, `ViewState`
- `slackline/attachment`: `Attachment`
- `slackline/file`: `File`
- `slackline/common`: `Reaction`
- `slackline/message`: `Message`, `MessageMetadata`, `BotProfile`
- `slackline/user`: `User`, `UserProfile`
- `slackline/team`: `Team`
- `slackline/usergroup`: `Usergroup`
- `slackline/conversation`: `Conversation`
- `slackline/bot`: `Bot`

## The schema language

Comments start with `#`. `//` is only valid as `///` or `////` docs.

```
//// Module docs (four slashes) go at the top of the generated module.
module slackline/user

/// Doc comments (three slashes) attach to the next declaration or field.
record User {
  /// Field docs come from the reference page.
  id: String
  team_id: String?               # `?` means optional: Option(String)
  "is-weird" as weird: Bool      # quoted json key and explicit Gleam name
  type = "user"                  # a constant: always encoded, not stored.
                                 # Decoding accepts it absent, fails on another value
}

/// Unions dispatch on a tag field, "type" unless you say otherwise.
union Block tag "type" {
  section Section { text: Text?, fields: List(Text)? }
  divider Divider
  "rich_text" RichText { elements: List(RichTextElement) }
  input Input(InputBlock)         # wrap a record. InputBlock must declare `type = "input"`
  .. UnknownBlock                 # catch-all. Every union gets one. A missing
                                  # tag also goes here, with tag ""
}

/// `tag "subtype" optional` sends a missing tag to the "" variant. Only
/// such unions can declare one.
union MessageEvent tag "subtype" optional {
  "" Plain { text: String? }
  bot_message BotMessage { bot_id: String? }
}

enum ButtonStyle {
  primary                         # constructor Primary
  "foo-bar" as FooBar
  .. UnknownButtonStyle           # open enum: keeps strings it does not know
}

/// Untagged alternatives, tried in order when decoding. A record without
/// required fields decodes any object, so it may only be the last one.
oneof UserRef {
  Id(String)
  Full(User)
}

method chat.postMessage {
  args {
    blocks: List(Block)           # override the type found in the docs
    text: String?                 # `?` forces optional, `!` forces required
    user_ids: List(String) json   # list encoding: `comma` (default) or `json`
    -as_user                      # drop an argument
  }
  response {
    channel: String
    ts: String
    message: Message?
  }
}
```

Types: `String`, `Int`, `Float` (accepts integers), `Bool`, `Value` (any
json), `List(T)`, `Dict(T)` (string keys), `List(T?)` / `Dict(T?)` (items
that may be json `null`, as `Option(T)`), `ResponseMetadata` (from the
hand-written `slackline` module), and any declared name. A type name may
only be declared once across all specs, so each concept has one type. The
generator rejects a second declaration. A bare name resolves to the type of
that name in any module except an `api/*` module. A type declared in an
`api/*` module is private to that module. Other modules can only refer to it
by its full name, such as `slackline/api/chat.TaskIcon`.

A method header is `method name [as function] [unauthenticated] {`. `as`
overrides the Gleam function name. `unauthenticated` marks methods that
authenticate with client credentials or a refresh token in the body
(`oauth.v2.access`, `tooling.tokens.rotate`, ...): their calls never send the
client's bearer token, which could make Slack reject them.

`deprecated "reason"` inside a method marks its function `@deprecated` with
that reason. Methods whose docs summary starts with "Deprecated" get the
attribute automatically; use the section when live behavior shows a method is
retired before the docs say so (`reminders.*`).

`response Nil` is for methods that only return `ok`. `response SomeRecord`
reuses a declared record. Leaving `response` out returns the raw `Value`.

Paginated methods take `cursor: String?` and declare
`response_metadata: ResponseMetadata?` in their response. Callers page with
the hand-written `slackline.next_page(call, response.response_metadata)`,
which returns the call for the next page, or `None`. The generator writes no
per-method helper.

A union variant that wraps a record (`input Input(InputBlock)`) encodes with
the record's own `_to_json`, so the record must declare the tag as a constant
field (`type = "input"`). Otherwise the generator rejects it. The `""` variant
of an optional tag must not declare the tag.

A decoder uses `decode.recursive` for every reference to a record or union
of the same module, because those types can refer back to the type being
decoded. References to other modules call `x_decoder()` directly. Gleam
modules cannot import each other in a cycle, so those references cannot be
part of a cycle.

The generator wraps doc comments on spaces at 80 columns. A word wider than
that stays on one line. The generator does not wrap a line so that the next
line starts with Markdown syntax (`- `, `1.`, `#`), and it does not change
fenced code blocks. The "Documented errors" list of each method leaves
out the codes that almost every method returns (`invalid_auth`,
`ratelimited`, ...). That list is a constant in the generator, not computed
from the docs.

The generator formats all of its output with one `gleam format` run on a
temporary directory. `--check` compares the same formatted text, so a check
passes exactly when a write would change nothing.

### What a method becomes

For `chat.postMessage` the generator writes, in `slackline/api/chat`:

- `pub type PostMessage`, an empty type naming the method. It is the first
  parameter of the method's `slackline.Call(method, response)`. When the name
  is taken (by a declared type, a response record or a Gleam builtin such as
  `List`) it gets a `Method` suffix: `conversations.ListMethod`.
- `PostMessageResponse` and its decoder, when the spec declares `response { .. }`.
- `pub fn post_message(channel channel: String, text text: String)`, taking the
  required arguments, labelled, in docs order. Its docs name the method type:
  "`chat.PostMessage` identifies this method in `slackline.Call`."

Optional arguments become setters in their own module,
`slackline/api/chat/post_message`: `pub fn thread_ts(call: Call(chat.PostMessage, r), thread_ts: String)`,
documented with the argument's docs. Methods without optional arguments get
no setter module. When a setter module has the name of a standard library
module (`list`, `dict`, `string`, ...), its module docs show how to import it
under another name: `import slackline/api/conversations/list as conversations_list`.

### Builders

`union Block builders { .. }` generates Lustre-style builders for a union
whose variants all wrap records. `builders "slackline/element"` puts them in
another module. Each variant gets a function named after its tag
(`block.section`). The function takes the required fields of the record
(labelled, in field order) and `with attrs: List(block.Attr(SectionBlock))`.
Override the arguments with `builder(field, ..)` after the variant:

```
union Element builders "slackline/element" {
  button Button(ButtonElement) builder(text, action_id)
}
```

Builder arguments can name optional fields. The builder wraps them in
`Some`. `PlainText` fields, as arguments and attributes, take a `String`.

Every other optional field becomes an attribute in a module named after the
variant: `slackline/block/section` has `section.block_id` and
`section.accessory`. An attribute is an `Attr(record)` that holds a function
to update the record of its variant. The module of the union declares `Attr`
once, for all of its builders, even when the builders are in another module:

```gleam
// slackline/element/button
pub fn url(url: String) -> block.Attr(block.ButtonElement) {
  block.attr(fn(it) { block.ButtonElement(..it, url: Some(url)) })
}
```

`block.attr` is public, so you can write your own attributes the same way.

A builder only takes attributes for its own record, so an attribute of
another variant is a compile error. The error names both records, for example
`Attr(ButtonElement)` and `Attr(DatepickerElement)`. Fields that many variants
share, such as `block_id`, get one attribute per variant.

The typed records, decoders and encoders do not change. You can still build
the records field by field and read them from payloads.

### Hand-written code

Hand-written helpers for a generated module go in `<name>.extra.gleam` beside
the spec. Its `import` lines are merged in and the rest is appended. Use it
for helpers like `block.mrkdwn(text)` that make common cases short.

## Conventions

- **Accuracy over convenience.** Every field, enum value and union variant
  should be traceable to the reference docs. Copy field descriptions from the
  docs into `///` comments, trimmed to a sentence or two.
- **`///` docs are for users.** Notes about the spec itself, such as a
  field the docs mark required but leave out of their example, go in `#`
  comments.
- **Optional by default for data Slack sends us.** Responses, events and
  objects only mark a field required when the docs say it is always present
  and it identifies the thing (`id`, `ts`, `channel`). Slack omits fields
  more often than its docs admit, and one missing required field fails the
  whole decode.
- **Required where Slack requires it for data we send.** Block Kit,
  views and other request bodies mark fields required exactly when Slack
  rejects the payload without them, so the type checker catches mistakes.
- **Open enums for data Slack sends** (`.. UnknownX`), closed enums for
  request-only values.
- **Every union has a catch-all.** It holds the raw json, so new Slack
  features never break decoding.
- **Type names must be unique across all specs.** Refer to the type that
  exists instead of declaring a copy. Two different things get two different
  names (`AdminWorkflowStep` and `WorkflowStep`).
- **Constructor names must be unique within a module**, across records,
  union variants, enum values and oneof variants. Prefer descriptive names
  (`SectionBlock`, `ButtonElement`) over clever ones.
- **Element names follow the Slack `type` string.** `datepicker` is
  `DatepickerElement`, `Datepicker`, `DatepickerAction` and
  `StateDatepicker`. `email_text_input` is `EmailTextInputElement`.
- **Free-form json is `Value`**, for example metadata payloads or workflow
  outputs.
- The docs examples are the best test data. Response examples in
  `methods.json` are decoded automatically by
  `test/slackline_examples_test.gleam`. If one fails, the type is wrong, or
  the example is. Note which. For other types, add gleeunit tests
  that decode the examples from the reference pages.
